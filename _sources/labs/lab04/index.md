(lab-04)=
# Лабораторна робота №4. Маршрутизація та спільний стан застосунку

**Контрольна точка:** CP4 — багатомаршрутний SPA зі спільним станом світлофора.

## Мета роботи

Навчитися організовувати React-застосунок як односторінковий застосунок (SPA, single-page application) із кількома
маршрутами, розділяти компоненти сторінок і макета та повторно використовувані
компоненти предметної області, а також винести стан світлофора до спільного власника,
коли одні й ті самі дані потрібні різним гілкам маршрутів.

У цій роботі Context з'являється не як «глобальне сховище про всяк випадок», а як
відповідь на конкретну проблему спільного стану: після появи сторінок
`/traffic-light` і `/stats` локальний стан CP3 більше не має одного природного
власника стану сторінки.

## Результати навчання

Після виконання роботи ви повинні вміти:

- пояснити, чим маршрут на стороні клієнта відрізняється від окремої HTML-сторінки;
- налаштувати базову маршрутизацію React SPA;
- створити спільний макет і навігацію для кількох сторінок;
- розділити компоненти сторінок, компоненти макета і повторно використовувані компоненти предметної області;
- пояснити, чому стан, потрібний різним гілкам маршрутів, потребує спільного власника;
- створити Context і провайдер контексту з обмеженою відповідальністю за світлофор;
- читати спільний стан та викликати дії предметної області із кількох сторінок через Context;
- зберігати поточний сигнал, лічильники, орієнтацію і стан автоматичного режиму під
  час переходів між маршрутами;
- пояснити, чому Context був зайвим у ЛР2, але стає виправданим у ЛР4.

## Передумови та початковий стан проєкту

Початкова точка цієї роботи — **CP3** після ЛР3:

- є повторно використовувані компоненти `Light`, `TrafficLights` і `StatsBar`;
- поточна фаза / активний сигнал зберігається у стані React;
- ручні натискання оновлюють сигнал і лічильники;
- орієнтація є керованою станом;
- автоматичний/ручний режим керується станом;
- `useEffect` створює таймер для автоматичного режиму і коректно виконує очищення;
- автоматичний цикл проходить `red → yellow → green → yellow → red`;
- повторні запуск і зупинка не породжують дубльованих таймерів;
- усі ці дані поки що живуть у локальному дереві однієї функціональної частини екрана.

Новий Vite-проєкт **не створюйте**. Продовжуйте той самий наскрізний проєкт
«Світлофор».

```{important}
Головна тема ЛР4 — **Router + спільний власник стану через Context**.
Маршрутизація тут потрібна не для того, щоб просто мати кілька URL, а щоб
побачити ситуацію, у якій локальний стан одного компонента сторінки перестає
бути достатнім.
```

## Теоретичний мінімум

### SPA і маршрут — не окремі HTML-файли

В односторінковому застосунку браузер завантажує каркас застосунку, а подальший
перехід між маршрутами змінює URL і те, які React-компоненти показуються на екрані,
без повного перезавантаження документа.

У цій роботі маршрут визначає, **інтерфейс якої сторінки показати для конкретного URL**.
Наприклад:

```text
/                → HomePage
/traffic-light   → TrafficLightPage
/stats           → StatsPage
невідомий URL    → NotFoundPage
```

Для базового SPA достатньо декларативної маршрутизації: браузерний маршрутизатор, набір маршрутів і
навігаційні посилання.

### Чому навігація має використовувати маршрутизатор

Звичайний HTML-link на кшталт:

```html
<a href="/stats">Статистика</a>
```

може спричинити повну навігацію браузера і нове завантаження застосунку. Для SPA
використовуйте навігацію засобами маршрутизатора, наприклад `NavLink` або `Link`.

Схематично:

```jsx
<NavLink to="/traffic-light">Світлофор</NavLink>
<NavLink to="/stats">Статистика</NavLink>
```

Так маршрутизатор змінює адресу всередині вже запущеного React-застосунку.

### Макет і `Outlet`

Кілька маршрутів часто мають спільну частину: заголовок, навігацію, нижній колонтитул або інший
каркас застосунку.

Замість дублювання цієї розмітки створіть компонент макета. Він показує спільний
інтерфейс і місце, де маршрутизатор повинен відтворити поточну дочірню сторінку.

```text
AppLayout
├── заголовок / навігація
└── Outlet
    ├── HomePage
    ├── TrafficLightPage
    ├── StatsPage
    └── NotFoundPage
```

`Outlet` — це місце для дочірнього маршруту, що відповідає поточній адресі.

### Чому Context не був потрібен у ЛР2

У ЛР2 уся функціональна частина жила у межах одного локального дерева:

```text
TrafficLights
├── Light × 3
└── StatsBar
```

`TrafficLights` був природним найближчим спільним власником стану. Дані можна було
передавати вниз через `props`, а події — вгору через функції зворотного виклику. Додавати Context
лише тому, що він існує в React, було б зайвим ускладненням.

Після появи маршрутизації структура змінюється:

```text
AppLayout
├── TrafficLightPage
│   └── TrafficLights
└── StatsPage
    └── StatsBar
```

`TrafficLightPage` і `StatsPage` — різні гілки маршрутів. Якщо стан залишити
всередині `TrafficLightPage`, то `StatsPage` не має природного доступу до нього,
а під час повторного монтування стан сторінки може скидатися.

Тепер виникає реальна потреба підняти власника стану **вище за обидві гілки маршрутів**.

### Context — канал доступу, а не магічний стан

Context сам по собі не замінює `useState` або `useEffect`. Він дає дочірнім
компонентам спосіб прочитати значення від найближчого провайдера контексту без ручного
прокидання однакових `props` через кожний проміжний компонент.

Схематично:

```text
TrafficLightsProvider
├── стан + ефекти + обробники предметної області
└── дерево Router
    ├── TrafficLightPage ── використовує Context
    └── StatsPage        ── використовує Context
```

Сам стан усе ще має конкретного власника — `TrafficLightsProvider`.

### Провайдер повинен відповідати лише за стан своєї предметної області

Не намагайтеся зробити один універсальний Context «для всього застосунку».
У цій роботі провайдер контексту має чітку відповідальність: **стан предметної області світлофора**.

До нього належать дані й дії, уже сформовані в CP2–CP3:

- поточна фаза / активний сигнал;
- лічильники ручних натискань;
- орієнтацію;
- автоматичний/ручний режим;
- дії для ручного вибору;
- дії запуску/зупинки або еквівалентне керування автоматичним режимом;
- життєвий цикл таймера, якщо він є частиною цієї поведінки предметної області.

До нього **не належать** майбутні облікові дані автентифікації, стан обміну із сервером або
випадкові налаштування інтерфейсу лише тому, що Context доступний у всьому піддереві.

### Провайдер контексту має переживати навігацію між маршрутами

Щоб спільний стан не скидався під час переходів між `/traffic-light` і `/stats`,
провайдер контексту повинен знаходитися **вище за елементи маршрутів, які перемикаються**.

Наприклад, корінь застосунку може мати таку форму:

```text
BrowserRouter
└── TrafficLightsProvider
    └── App
        └── Routes
```

або еквівалентну структуру з тією самою межею володіння станом.

Якщо ж провайдер контексту створюється всередині `TrafficLightPage`, то під час виходу з
цього маршруту він може демонтуватися разом зі станом — і Context не розв'яже
проблему.

### Компоненти представлення не повинні знати Router

`Light`, `TrafficLights` і `StatsBar` уже мають відповідальність за предметну логіку та інтерфейс.
Не потрібно додавати до них навігацію лише тому, що застосунок тепер має
маршрути.

Краще, щоб компоненти сторінок були межею інтеграції:

```text
TrafficLightPage
├── використовує спільний стан світлофора
└── передає потрібні props у TrafficLights

StatsPage
├── використовує спільний стан світлофора
└── передає потрібні props у StatsBar
```

Так повторно використовувані компоненти можна відтворювати й тестувати незалежно від Router.

### Збереження стану між маршрутами та між перезавантаженнями — різні речі

Після цієї роботи переходи між маршрутами не повинні скидати спільний стан світлофора. Але це **не означає**, що стан уже зберігається між перезавантаженнями браузера.

```text
навігація маршрутами      → стан CP4 зберігається
повне перезавантаження    → стан може початися заново
```

Збереження даних на сервері з'явиться в ЛР5. Не підміняйте її в цій
роботі випадковим `localStorage`, якщо це не є вашим окремим додатковим
експериментом.

## Постановка задачі

Перетворіть CP3 із одного локального екрана функціональної частини на багатомаршрутний SPA зі
спільним станом світлофора.

Після виконання роботи застосунок повинен мати щонайменше такі маршрути:

| URL | Призначення |
|---|---|
| `/` | головна сторінка / огляд застосунку |
| `/traffic-light` | світлофор, елементи ручного керування, запуск/зупинка, орієнтація |
| `/stats` | статистика та відображення спільного стану лише для читання |
| будь-який інший | сторінка для невідомої адреси / Not Found |

Додатково:

1. усі сторінки використовують спільний макет застосунку й навігацію;
2. стан світлофора має одного власника стану у `TrafficLightsProvider` або провайдера контексту з
   еквівалентною відповідальністю;
3. `/traffic-light` і `/stats` бачать один і той самий поточний сигнал і лічильники;
4. навігація між маршрутами не скидає поточний сигнал, лічильники, орієнтацію або
   стан автоматичного режиму;
5. автоматичний режим не повинен випадково зупинятися лише тому, що користувач
   перейшов на `/stats`, якщо провайдер контексту лишається змонтованим;
6. компоненти представлення не стають залежними від Router без необхідності;
7. головна сторінка та сторінка для невідомої адреси не стають власниками стану світлофора.

```{note}
У ЛР4 ми перевіряємо збереження стану **лише в пам'яті поточної вкладки браузера**. Якщо ви
оновили вкладку браузера і стан повернувся до початкових значень, це ще не
помилка CP4. Збереження даних між перезавантаженнями буде окремою темою ЛР5.
```

## Виконання

### Крок 1. Додайте React Router у наявний проєкт

Не створюйте новий каркас застосунку. Додайте залежність маршрутизації до того
самого Vite-проєкту CP3.

Для декларативного режиму використайте актуальний пакет React Router:

```bash
npm install react-router
```

Підключіть браузерного маршрутизатора на верхньому рівні дерева застосунку.

Мінімальна ідея:

```jsx
import { BrowserRouter } from "react-router"

<BrowserRouter>
  <App />
</BrowserRouter>
```

Не копіюйте цей фрагмент механічно поверх свого `main.jsx`. Збережіть уже наявний
`StrictMode` та інші кореневі обгортки, якщо вони є.

**Перевірка 1:** застосунок запускається після встановлення Router, а поточна
поведінка CP3 ще не зламана.

### Крок 2. Створіть компоненти сторінок і структуру маршрутів

Створіть окремі компоненти сторінок щонайменше для:

- `HomePage`;
- `TrafficLightPage`;
- `StatsPage`;
- `NotFoundPage` або еквівалентної сторінки для невідомої адреси.

Назви директорій (`pages`, `Pages` тощо) не є метою роботи. Важливіше, щоб у
структурі коду було видно різницю між **інтеграцією на рівні сторінки** і повторно використовуваними
компонентами.

Для декларативної маршрутизації достатньо `Routes` і `Route`:

```jsx
<Routes>
  <Route path="/" element={/* ... */} />
  <Route path="/traffic-light" element={/* ... */} />
  <Route path="/stats" element={/* ... */} />
  <Route path="*" element={/* ... */} />
</Routes>
```

Це лише схема структури маршрутів, а не готове рішення з вашими імпортами й компонентами.

**Перевірка 2:** введення кожної потрібної URL-адреси в адресний рядок браузера показує
відповідну сторінку, а невідомий URL має контрольований інтерфейс для невідомої адреси.

### Крок 3. Створіть спільний макет і навігацію

Винесіть спільний каркас застосунку в компонент макета.

Макет має щонайменше містити навігацію до:

- `/`;
- `/traffic-light`;
- `/stats`.

Для вкладеної структури маршрутів макет може містити `Outlet`:

```jsx
function AppLayout() {
  return (
    <>
      <nav>{/* NavLink ... */}</nav>
      <main>
        <Outlet />
      </main>
    </>
  )
}
```

Використайте `NavLink` або `Link`, а не повне перезавантаження браузера через звичайні
`href` для внутрішньої SPA-навігації.

За бажанням позначайте активний пункт меню через можливості `NavLink`, але
складне оформлення навігації не є головною метою ЛР4.

**Перевірка 3:** усі потрібні сторінки доступні з навігації інтерфейсу без ручного
редагування URL і без повного перезавантаження застосунку.

### Крок 4. Визначте склад спільного стану світлофора

До створення Context випишіть, які дані реально повинні переживати
навігацію між маршрутами і бути видимими кільком сторінкам.

Для CP4 це щонайменше:

```text
currentPhase / currentSignal
clickCounters
orientation
isAutomatic
```

Також випишіть дії предметної області, які потрібні компонентам-споживачам. Наприклад:

```text
selectSignal(...)
startAutomatic()
stopAutomatic()
toggleOrientation()
```

Точні назви можуть відрізнятися. Важливо, щоб Context описував можливості предметної області,
а не випадковий набір усіх локальних функцій оновлення стану проєкту.

```{important}
Не додавайте в `TrafficLightsContext` майбутній стан автентифікації, серверні запити або
будь-які дані «про запас». Context повинен мати одну зрозумілу відповідальність.
```

**Перевірка 4:** ви можете одним реченням пояснити, які дані належать
`TrafficLightsProvider`, а які — ні.

### Крок 5. Перенесіть стан та життєвий цикл таймера до `TrafficLightsProvider`

Створіть Context і провайдер контексту, який стане спільним власником для стану CP3.

Базова структура може виглядати так:

```jsx
const TrafficLightsContext = createContext(null)

function TrafficLightsProvider({ children }) {
  // стан CP2/CP3
  // ефект + очищення таймера CP3
  // обробники предметної області

  const value = {
    // спільний стан
    // дії предметної області
  }

  return (
    <TrafficLightsContext.Provider value={value}>
      {children}
    </TrafficLightsContext.Provider>
  )
}
```

Це **структурний каркас**, а не повний код провайдера контексту. Перенесіть у нього вже
працюючу CP3-логіку без зміни поведінки предметної області.

Особливо перевірте:

- ефект таймера й очищення не загубилися під час рефакторингу;
- автоматичні кроки таймера не почали збільшувати лічильники ручних натискань;
- орієнтація і поточна фаза не створили дубльованих копій стану;
- провайдер контексту не створюється заново для кожної окремої сторінки.

**Перевірка 5:** після рефакторингу поведінка CP3 працює так само, але власник стану
тепер знаходиться вище сторінок маршрутів.

### Крок 6. Розмістіть провайдер контексту вище за гілки маршрутів

Розмістіть `TrafficLightsProvider` так, щоб `TrafficLightPage` і `StatsPage`
бачили **той самий екземпляр провайдера контексту**.

Один із можливих варіантів дерева застосунку:

```text
BrowserRouter
└── TrafficLightsProvider
    └── App
        └── Routes
            └── AppLayout
                ├── HomePage
                ├── TrafficLightPage
                ├── StatsPage
                └── NotFoundPage
```

Не розміщуйте провайдер контексту всередині `TrafficLightPage`, якщо очікуєте збереження стану
під час переходу на `/stats`.

**Перевірка 6:** встановіть непочатковий сигнал, кілька разів змініть лічильники
та орієнтацію, увімкніть або вимкніть автоматичний режим, перейдіть на `/stats` і
назад. Спільні значення не повинні скидатися.

### Крок 7. Підключіть `TrafficLightPage` до Context

`TrafficLightPage` з’єднує спільний стан з інтерактивним інтерфейсом світлофора.
Вона повинна отримати спільний стан і дії із Context і передати потрібні дані
повторно використовуваним компонентам.

Наприклад, сторінка може:

- прочитати поточну фазу / сигнал;
- прочитати орієнтацію;
- прочитати стан автоматичного режиму;
- отримати обробники ручного вибору, запуску/зупинки й зміни орієнтації;
- передати ці дані в `TrafficLights`, елементи керування та інші дочірні компоненти.

Сам `TrafficLights` не зобов'язаний викликати хуки маршрутизатора. Він може й надалі
працювати через зрозумілий контракт `props`.

**Перевірка 7:** інтерактивна поведінка CP3 працює на `/traffic-light`, а повторно використовувані
компоненти представлення не потребують знань про поточну URL-адресу.

### Крок 8. Підключіть `StatsPage` до того самого Context

`StatsPage` повинна читати ті самі лічильники та інші потрібні спільні значення.

Вона має щонайменше показувати:

- лічильники `red`, `yellow`, `green`;
- загальну кількість ручних натискань як похідне значення;
- поточний сигнал / фазу;
- орієнтацію;
- стан автоматичного/ручного режиму.

Якщо у вас уже є `StatsBar`, використайте його повторно або виділіть із нього
частину представлення. Не створюйте на `StatsPage` нову незалежну копію лічильників.

**Перевірка 8:** змініть стан на `/traffic-light`, відкрийте `/stats` і
переконайтеся, що сторінка одразу показує ті самі значення без дубльованого стану.

### Крок 9. Перевірте збереження стану під час навігації як сценарій

Виконайте послідовність:

1. відкрийте `/traffic-light`;
2. зробіть кілька ручних натискань;
3. змініть орієнтацію;
4. увімкніть автоматичний режим і дочекайтеся кількох переходів;
5. перейдіть на `/stats`;
6. переконайтеся, що лічильники, поточна фаза та режим узгоджені;
7. поверніться на `/traffic-light`;
8. перевірте, що стан не повернувся до початкових значень;
9. відкрийте невідомий URL і перевірте сторінку для невідомої адреси;
10. поверніться через навігацію, а не через створення нового стану застосунку.

Якщо стан скидається, перевірте насамперед **де саме змонтований провайдер контексту**, а не
намагайтеся «лікувати» проблему додатковим Context або копіюванням стану.

**Перевірка 9:** весь сценарій проходить без скидання спільного стану і без дубльованих
провайдерів контексту.

## Контрольні точки виконання

Перед завершенням роботи послідовно перевірте:

1. застосунок має маршрути `/`, `/traffic-light`, `/stats` і маршрут для невідомої адреси;
2. навігація працює як SPA-навігація;
3. є спільний макет, який не дублюється в кожній сторінці;
4. `TrafficLightsProvider` має одну чітку відповідальність у предметній області;
5. власник поточної фази, лічильників, орієнтації та стану автоматичного режиму — провайдер контексту;
6. життєвий цикл таймера CP3 збережений після перенесення стану;
7. `TrafficLightPage` і `StatsPage` отримують узгоджений спільний стан;
8. навігація між маршрутами не скидає спільний стан;
9. компоненти представлення не стали залежними від Router без потреби;
10. сторінки Home/NotFound не володіють станом світлофора;
11. дані автентифікації/серверної частини не додані до Context світлофора;
12. перезавантаження браузера не видається за вимогу збереження між перезавантаженнями в CP4.

## Самоперевірка

Дайте відповіді на запитання і будьте готові пояснити їх під час захисту:

1. Що означає SPA у контексті вашого застосунку?
2. Яку задачу розв'язує `BrowserRouter`?
3. Чому для внутрішньої навігації краще використати `NavLink`/`Link`, а не
   звичайний `<a href>`?
4. Яку роль виконує `Outlet` у маршруті макета?
5. Чому Context не був потрібний у ЛР2?
6. Яка нова проблема з'явилася після поділу застосунку на `/traffic-light` і
   `/stats`?
7. Де тепер знаходиться власник стану світлофора?
8. Чому Context не є сам по собі заміною `useState`?
9. Що відбудеться, якщо `TrafficLightsProvider` розмістити всередині
   `TrafficLightPage`?
10. Які значення входять до Context і чому саме вони?
11. Які дані свідомо **не** входять до цього Context?
12. Де тепер живе ефект таймера CP3 і чому?
13. Чому `TrafficLights` і `StatsBar` бажано залишати незалежними від Router?
14. Чим збереження стану між маршрутами відрізняється від збереження стану між
    перезавантаженнями браузера?
15. Як ви перевірили, що `/traffic-light` і `/stats` бачать один спільний стан?
16. Чому універсальний «Context для всього» гірший за контекст конкретної предметної області
    `TrafficLightsProvider`?

## Критерії приймання

Робота вважається виконаною, якщо одночасно виконані всі умови:

- застосунок продовжує CP3 без створення нового незалежного проєкту;
- React Router інтегрований у наявний Vite-застосунок;
- доступні маршрути `/`, `/traffic-light`, `/stats` і контрольований маршрут для невідомої адреси;
- є спільний макет і навігація;
- внутрішня навігація між потрібними сторінками працює як SPA-навігація;
- спільний стан світлофора має одного спільного власника — `TrafficLightsProvider`;
- поточна фаза / активний сигнал, лічильники, орієнтація і стан автоматичного режиму
  належать спільному власнику стану, а не окремим сторінкам маршрутів;
- `TrafficLightPage` і `StatsPage` споживають узгоджений стан через Context;
- переходи `/traffic-light ↔ /stats` не скидають спільні значення;
- ефект таймера й очищення CP3 продовжують працювати після рефакторингу;
- автоматичний режим не створює дубльовані таймери під час навігації між маршрутами;
- лічильники ручних натискань не збільшуються від автоматичних кроків таймера;
- компоненти представлення не мають зайвої відповідальності за маршрутизацію;
- сторінки Home та Not Found не є власниками стану світлофора;
- Context світлофора не містить відповідальності за автентифікацію/серверну частину;
- студент може пояснити розташування провайдера контексту і причину появи Context саме у ЛР4.

## Додаткове завдання

Після виконання обов'язкових вимог додайте **ще один маршрут лише для читання**, який
споживає той самий Context світлофора.

Наприклад:

```text
/status
```

На цій сторінці можна компактно показати:

- поточний сигнал;
- автоматичний/ручний режим;
- орієнтацію;
- загальну кількість ручних натискань.

Додатковий маршрут **не повинен** створювати новий провайдер контексту або власні копії
стану світлофора. Його мета — показати, що вже створений спільний Context
підтримує новий компонент-споживач без зміни власника стану.

## Поза основним обсягом ЛР4

У цій роботі не потрібно робити стан світлофора між перезавантаженнями браузера.
Серверне збереження та GAS API з'являться в ЛР5.

Так само поза основним обсягом ЛР4 залишаються:

- завантажувачі/дії React Router або інша архітектура отримання даних;
- `json-server` чи інша тестова серверна частина як обов'язковий елемент;
- Tailwind CSS і DaisyUI як система інтерфейсу;
- автентифікація і захищені маршрути;
- виробнича конфігурація розгортання для прямих запитів до вкладених SPA-адрес.

Зосередьтеся на двох пов'язаних питаннях:

1. **яка сторінка відповідає поточному URL;**
2. **де повинен жити стан, якщо він потрібний кільком сторінкам.**

## Результат

**CP4:** багатомаршрутний React-застосунок із SPA-маршрутизацією та маршрутами `/`, `/traffic-light`, `/stats` і сторінкою для невідомої адреси, спільними макетом і навігацією та `TrafficLightsProvider`, який є одним власником стану
для поточної фази, лічильників, орієнтації, стану автоматичного режиму і пов'язаного
життєвого циклу таймера CP3. `TrafficLightPage` і `StatsPage` бачать один спільний стан,
навігація між маршрутами не скидає його, а компоненти представлення залишаються
відокремленими від Router настільки, наскільки це дозволяє їхня відповідальність.

Цей стан проєкту є вхідною точкою для ЛР5, де спільний стан застосунку буде
пов'язано з даними, збереженими на сервері, через обмежений GAS API.
