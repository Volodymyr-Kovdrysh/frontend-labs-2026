3. Лабораторна робота №3. Поведінка в часі, ефекти та анімація#

Контрольна точка: CP3 — автоматичний світлофор із керованим життєвим циклом часової поведінки.

3.1. Мета роботи#

Навчитися додавати до React-застосунку поведінку, яка відбувається з часом, а не лише у відповідь на безпосередню дію користувача: запускати й зупиняти таймер через useEffect, коректно виконувати функцію очищення (cleanup), керувати залежностями ефекту та відображати зміни стану за допомогою візуального переходу.

3.2. Результати навчання#

Після виконання роботи ви повинні вміти:

  • пояснити різницю між оновленням, керованим подією, і побічним ефектом;

  • використовувати useEffect для створення ефекту React (Effect) і синхронізації компонента з API таймерів браузера;

  • пояснити роль масиву залежностей та визначати реактивні значення, від яких залежить ефект;

  • повертати функцію очищення, що зупиняє попередній таймер;

  • організувати «Запустити» / «Зупинити», не створюючи паралельних інтервалів;

  • реалізувати автоматичний цикл сигналів red → yellow → green → yellow → red;

  • зберегти ручну взаємодію і статистику з CP2;

  • використовувати CSS-перехід або іншу анімацію як відображення стану, а не як друге джерело стану застосунку.

3.3. Передумови та початковий стан проєкту#

Початковою точкою є CP2 — результат ЛР2. У застосунку вже мають бути:

  • компоненти TrafficLights, Light і StatsBar;

  • локальний власник стану світлофора;

  • поточний/активний сигнал;

  • лічильники для red, yellow і green;

  • ручне натискання через функцію зворотного виклику з Light до власника стану;

  • керована орієнтація vertical / horizontal;

  • похідний інтерфейс без дублювання джерел актуального стану.

Не створюйте новий Vite-проєкт і не копіюйте попередню роботу в інший каталог. Продовжуйте той самий наскрізний проєкт «Світлофор».

Важливо

ЛР3 не замінює поведінку ЛР2, керовану подіями. Вона додає ще один спосіб зміни того самого стану предметної області — автоматичне перемикання з часом.

3.4. Теоретичний мінімум#

3.4.1. Подія і ефект — не одне й те саме#

Обробник події виконує код тому, що користувач здійснив конкретну дію: натиснув кнопку, клікнув на сигнал або змінив елемент керування.

подія користувача → обробник → оновлення стану → відтворення

Ефект запускається не як пряме продовження натискання. Він описує синхронізацію компонента з чимось поза звичайним циклом відтворення React: API таймерів, мережею, підпискою або іншим зовнішнім механізмом.

Для цієї лабораторної таким зовнішнім механізмом є браузерний таймер:

відтворення → налаштування ефекту → таймер працює → функція зворотного виклику таймера → оновлення стану → відтворення

Тому «Запустити» не повинен безпосередньо створювати нескінченну кількість setInterval. Обробник події змінює стан автоматичного режиму, а ефект уже синхронізує наявність таймера з цим станом.

3.4.2. useEffect: налаштування, залежності та очищення#

Базова форма ефекту React:

useEffect(() => {
  // налаштування

  return () => {
    // очищення
  };
}, [/* залежності */]);

У цій моделі:

  • налаштування запускає зовнішній процес;

  • залежності визначають, коли попереднє налаштування більше не відповідає поточним реактивним значенням;

  • очищення зупиняє або скасовує те, що створило попереднє налаштування.

Для таймера налаштування й очищення мають бути симетричними:

setInterval(...)  ↔  clearInterval(...)

Очищення виконується не лише під час демонтування компонента. React також викликає його перед повторним запуском ефекту, якщо змінилися залежності. Саме ця властивість дозволяє безпечно реагувати на «Запустити», «Зупинити» або зміну інтервалу.

Офіційна документація React описує ефект саме як синхронізацію із зовнішньою системою та вимагає, щоб очищення зупиняло або скасовувало те, що створило налаштування: React: useEffect.

3.4.3. Таймер має життєвий цикл#

Розглянемо абстрактний приклад, не пов’язаний із готовим рішенням світлофора:

useEffect(() => {
  if (!running) {
    return;
  }

  const timerId = setInterval(() => {
    setTick((previous) => previous + 1);
  }, delay);

  return () => clearInterval(timerId);
}, [running, delay]);

Тут таймер існує лише тоді, коли running === true.

Коли running змінюється з true на false, React спочатку виконує очищення попереднього ефекту, й інтервал припиняється. Повторне натискання «Запустити» створить новий таймер, а не додасть ще один поверх старого.

Попередження

Не зберігайте timerId як глобальну змінну модуля й не використовуйте таймер як прихований змінний стан. Єдиним джерелом актуального стану для режиму роботи має залишатися стан React, а ефект лише синхронізує з ним зовнішній таймер.

3.4.4. Залежності — це частина логіки ефекту#

Масив залежностей не є списком, який потрібно «підібрати, щоб перестало перерендерюватися». Він описує реактивні значення, що використовуються під час налаштування й очищення ефекту.

Якщо ефект залежить від isAutomatic та intervalMs, ці значення повинні бути узгоджені з масивом залежностей. Якщо всередині ефекту використовується стан, який оновлюється на основі попереднього значення, функціональна форма оновлення часто дозволяє не перетворювати це значення на причину створення нового інтервалу після кожного кроку таймера.

Наприклад:

setIndex((previous) => /* наступний index на основі previous */);

Це та сама функціональна форма оновлення, яку ви вже використовували в ЛР2 для стану, що залежить від попереднього значення.

3.4.5. Чому yellow у циклі потребує позиції, а не лише кольору#

Базовий цикл має чотири фази:

red → yellow → green → yellow → red

Колір yellow зустрічається двічі. Якщо зберігати тільки рядок currentSignal === "yellow", неможливо однозначно визначити, що буде далі: green чи red.

Тому для автоматичного циклу зручно мати позицію у послідовності, наприклад індекс фази, а видимий колір отримувати як похідне значення:

phaseIndex → cycle[phaseIndex] → currentSignal

Це продовжує принцип ЛР2: не створюйте два незалежні стани для одного факту, якщо одне значення можна однозначно вивести з іншого.

Точну структуру cycle і назву стану оберіть самостійно. Важливо, щоб у застосунку було єдине зрозуміле джерело актуального стану для поточної фази.

3.4.6. Strict Mode як перевірка очищення#

У режимі розробки React Strict Mode може виконати додатковий цикл налаштування → очищення → налаштування для ефекту. Це допомагає виявити некоректне очищення. Якщо через це інтервал запускається двічі, проблему потрібно виправляти в життєвому циклі ефекту, а не вимикати Strict Mode.

Офіційна документація React прямо описує цю додаткову перевірку в режимі розробки: React: <StrictMode>.

3.4.7. Анімація відображає стан#

Візуальний перехід повинен відповідати фактичному стану світлофора. Наприклад, активна лампа може змінювати opacity, filter, transform або box-shadow через CSS-перехід.

зміна стану → нові CSS-класи/props → візуальний перехід

Небажана модель:

анімація завершилась → «вирішила», який тепер стан предметної області

У першому випадку стан React залишається єдиним джерелом актуального стану. У другому анімація починає керувати логікою предметної області, і UI може розійтися з фактичним станом.

3.5. Постановка задачі#

Потрібно розширити CP2 автоматичним режимом роботи світлофора.

Після виконання роботи застосунок повинен мати таку поведінку:

  1. ручний режим з ЛР2 збережений;

  2. є стан, який однозначно показує, чи увімкнено автоматичний режим;

  3. кнопка «Запустити» запускає автоматичне перемикання;

  4. кнопка «Зупинити» зупиняє автоматичне перемикання;

  5. базова послідовність фаз: red → yellow → green → yellow → red;

  6. одночасно працює не більше одного таймера автоматичного режиму;

  7. після «Зупинити» поточний сигнал залишається видимим і більше сам не змінюється;

  8. після «Зупинити» ручне натискання і лічильники з CP2 продовжують працювати;

  9. орієнтація і StatsBar з CP2 не скидаються під час запуску/зупинки;

  10. кожна автоматична зміна активного сигналу має помітний візуальний перехід;

  11. анімація не зберігає окремий стан предметної області і не визначає наступну фазу.

Примітка

У базовому варіанті під час автоматичного режиму ручний вибір сигналів можна тимчасово вимкнути. Після «Зупинити» ручна взаємодія CP2 має працювати без зміни своєї семантики. Якщо ви дозволяєте ручний вибір і під час автоматичного режиму, поведінка наступного кроку таймера повинна бути детермінованою та поясненою.

3.6. Виконання#

3.6.1. Крок 1. Визначте модель фаз автоматичного циклу#

Почніть не з таймера, а з послідовності предметної області.

Опишіть чотири фази циклу в одному місці:

red → yellow → green → yellow

Після останньої фази наступною знову стає red.

Оскільки yellow повторюється, модель має дозволяти відрізнити дві позиції циклу. Один із простих варіантів — зберігати індекс поточної фази та отримувати видимий колір із послідовності.

Не створюйте окремий незалежний стан одночасно для phaseIndex і currentSignal, якщо currentSignal повністю визначається індексом.

При переході з CP2 вам може знадобитися невеликий рефакторинг власника стану: ручний вибір тепер має встановлювати не лише «колір», а узгоджену позицію циклу. Для red і green позиція однозначна. Для yellow виберіть одну узгоджену позицію для ручного вибору й використовуйте її послідовно.

Перевірка 1: без таймера ви можете вручну змінити фазу/індекс і однозначно отримати видимий red, yellow або green; у стані немає двох незалежних джерел поточної фази.

3.6.2. Крок 2. Додайте стан автоматичного режиму#

Додайте логічний стан на кшталт isAutomatic.

«Запустити» і «Зупинити» повинні лише змінювати цей стан. Не створюйте інтервал безпосередньо всередині обробника натискання кнопки «Запустити».

Бажана модель:

Подія «Запустити» → isAutomatic = true
Подія «Зупинити»  → isAutomatic = false

а життєвий цикл таймера належить ефекту.

Щоб поведінка була однозначною, елемент керування, який уже відповідає поточному режиму, може бути disabled: наприклад, повторний «Запустити» під час автоматичного режиму не повинен створювати новий таймер.

Перевірка 2: багаторазове натискання «Запустити» не створює видимого прискорення або кількох паралельних циклів; «Зупинити» переводить застосунок у ручний режим.

3.6.3. Крок 3. Створіть ефект для життєвого циклу таймера#

Додайте useEffect на рівні компонента-власника стану, який керує автоматичним режимом і поточною фазою.

Ефект повинен:

  1. нічого не запускати, якщо автоматичний режим вимкнений;

  2. під час налаштування створювати один таймер;

  3. у функції зворотного виклику переходити до наступної фази циклу;

  4. повертати функцію очищення, яка зупиняє саме цей таймер;

  5. мати масив залежностей, що відповідає реактивним значенням ефекту.

Не копіюйте готовий абстрактний setTick із теоретичного прикладу буквально: ваша функція зворотного виклику повинна оновлювати стан предметної області світлофора.

Для базового варіанта використайте одну зрозумілу тривалість фази, наприклад кілька секунд. Конкретне число не є результатом навчання — важливий життєвий цикл.

Перевірка 3: після «Запустити» сигнал автоматично проходить щонайменше два повні цикли у правильному порядку; після «Зупинити» автоматичні зміни припиняються.

3.6.4. Крок 4. Перевірте очищення, а не лише видимий результат#

Сам факт, що кнопка «Зупинити» «ніби працює», ще не доводить коректний життєвий цикл.

Перевірте сценарій:

  1. «Запустити»;

  2. дочекайтеся кількох перемикань;

  3. «Зупинити»;

  4. знову «Запустити»;

  5. повторіть цикл кілька разів.

Якщо після кількох повторів сигнали починають змінюватися швидше або непередбачувано, старі таймери, імовірно, не очищаються.

Додатково будьте готові пояснити:

  • який ресурс створює налаштування;

  • яке значення ідентифікує цей ресурс;

  • де саме викликається clearInterval або еквівалентна функція очищення;

  • коли React виконає очищення при зміні автоматичного режиму;

  • чому очищення потрібне, навіть якщо компонент зараз не демонтується.

Важливо

У React Strict Mode середовище розробки може навмисно виконати додатковий налаштування → очищення → налаштування. Коректний ефект повинен витримувати це без появи другого активного таймера.

Перевірка 4: повторення «Запустити → Зупинити → Запустити» не змінює фактичну швидкість циклу й не створює дубльованих таймерів.

3.6.5. Крок 5. Збережіть ручну взаємодію і статистику CP2#

Автоматичний режим не повинен руйнувати вже готову модель, керовану подіями.

У базовому варіанті достатньо такої політики:

  • під час автоматичного режиму ручний вибір Light може бути недоступним;

  • автоматичний перехід не збільшує лічильники ручних натискань;

  • StatsBar продовжує показувати накопичену статистику ручних взаємодій;

  • «Зупинити» повертає можливість ручного вибору;

  • ручне натискання після «Зупинити» знову змінює активний сигнал і збільшує відповідний лічильник;

  • орієнтацію можна перемикати без скидання лічильників або поточної фази.

Такий поділ не змішує дві різні події: автоматичний крок таймера і натискання користувача.

Якщо ви обираєте іншу політику — наприклад, дозволяєте ручне натискання під час автоматичного режиму — вона має бути детермінованою і не повинна породжувати другий таймер або дубльований стан.

Перевірка 5: після кількох автоматичних циклів натисніть «Зупинити», виконайте ручні натискання і змініть орієнтацію. CP2-функції працюють, лічильники відображають саме ручні взаємодії і не були скинуті автоматичним режимом.

3.6.6. Крок 6. Додайте візуальний перехід#

Зробіть зміну активного сигналу візуально помітною.

Базовий варіант не потребує додаткової JavaScript-бібліотеки. Достатньо CSS-переходу або CSS-анімації, пов’язаної з класом активного Light.

Можливі властивості для переходу:

  • opacity;

  • filter;

  • transform;

  • box-shadow;

  • комбінація кількох властивостей.

Важлива умова: Стан React визначає, який сигнал активний, а CSS визначає, як ця зміна виглядає.

За бажанням після виконання обов’язкових вимог можна використати бібліотеку motion, але вона не повинна ставати новим джерелом стану або вимагати зміни життєвого циклу таймера.

Перевірка 6: і ручний вибір, і автоматичний перехід мають видимий зворотний зв’язок інтерфейсу, але після вимкнення CSS/анімації послідовність предметної області все одно працює правильно.

3.6.7. Крок 7. Проаналізуйте залежності ефекту#

Перед завершенням роботи відкрийте ваш useEffect і для кожного реактивного значення, яке використовується всередині налаштування/очищення, поясніть його зв’язок із масивом залежностей.

Не змінюйте залежності методом «спробував — попередження зникло». Пояснення повинно виходити з логіки ефекту.

Перевірте також, що функція зворотного виклику таймера не змушує ефект створювати новий інтервал після кожного автоматичного кроку таймера без потреби. Якщо наступна фаза залежить від попередньої, використайте функціональну форму оновлення стану або іншу узгоджену модель, яка не створює зайву залежність лише для читання попереднього стану.

Перевірка 7: студент може назвати залежності ефекту, пояснити кожну з них і показати, що інтервал не накопичується під час роботи.

3.7. Контрольні точки виконання#

Перед завершенням роботи послідовно перевірте:

  1. CP2-компоненти та статистику ручних взаємодій збережені;

  2. поточна фаза має єдине джерело актуального стану, а видимий сигнал узгоджений із ним;

  3. є окремий стан автоматичного/ручного режиму;

  4. «Запустити» / «Зупинити» змінюють стан режиму, а не керують глобальним таймером вручну;

  5. ефект створює таймер тільки для автоматичного режиму;

  6. функція очищення зупиняє попередній таймер;

  7. цикл проходить red → yellow → green → yellow → red у правильному порядку;

  8. повторні запуски й зупинки не прискорюють цикл і не створюють дубльованих таймерів;

  9. після «Зупинити» ручне натискання, лічильники та орієнтація CP2 працюють;

  10. автоматичні кроки таймера не маскуються під ручні натискання у статистиці;

  11. візуальний перехід походить від активного стану;

  12. залежності ефекту можна пояснити через фактичні реактивні значення.

3.8. Самоперевірка#

Дайте відповіді на запитання і будьте готові пояснити їх під час захисту:

  1. Чим ефект відрізняється від обробника події у вашому застосунку?

  2. Чому «Запустити» не повинен створювати setInterval напряму в обробнику натискання?

  3. Який стан визначає, чи повинен таймер існувати?

  4. Що саме робить налаштування вашого ефекту?

  5. Що саме робить очищення і коли React його викликає?

  6. Чому очищення може виконатися навіть без демонтування компонента?

  7. Які реактивні значення входять до масиву залежностей вашого ефекту і чому?

  8. Чому функціональна форма оновлення корисна всередині функції зворотного виклику таймера?

  9. Чому одного значення "yellow" недостатньо, щоб визначити наступну фазу чотирифазного циклу?

  10. Де знаходиться єдине джерело актуального стану для поточної фази?

  11. Як повторення «Запустити/Зупинити» допомагає виявити дубльовані таймери?

  12. Чому автоматичний крок таймера не повинен автоматично збільшувати лічильник ручних натискань?

  13. Що станеться з поведінкою предметної області, якщо прибрати CSS-перехід?

  14. Чому анімація не повинна визначати наступний стан предметної області?

  15. Чому додатковий налаштування → очищення → налаштування у Strict Mode не є причиною вимикати Strict Mode?

3.9. Критерії приймання#

Робота вважається виконаною, якщо одночасно виконані всі умови:

  • застосунок продовжує CP2 без створення нового незалежного проєкту;

  • є явний стан автоматичного/ручного режиму;

  • поточна фаза / активний сигнал має єдине узгоджене джерело актуального стану;

  • «Запустити» запускає автоматичний цикл, а «Зупинити» його зупиняє;

  • автоматична послідовність відповідає red → yellow → green → yellow → red;

  • таймер створюється в ефекті, а не як прихований глобальний змінний ресурс;

  • Ефект повертає функцію очищення, яка зупиняє створений таймер;

  • повторення «Запустити/Зупинити» не породжує дубльованих таймерів і не змінює швидкість циклу;

  • після «Зупинити» ручний вибір і лічильники CP2 продовжують працювати;

  • автоматичні кроки таймера не збільшують лічильник ручних натискань у базовій реалізації;

  • орієнтація не скидає поточну фазу або статистику;

  • активний сигнал має помітний візуальний перехід;

  • візуальна анімація походить від стану React і не визначає стан предметної області;

  • студент може пояснити масив залежностей, життєвий цикл налаштування/очищення і причину відсутності дубльованих таймерів.

3.10. Додаткове завдання#

Після виконання обов’язкових вимог реалізуйте різну тривалість фаз. Наприклад, red, green і yellow можуть мати різні значення тривалості.

Для цього зручніше перейти від «одного інтервалу назавжди» до моделі, у якій поточна фаза визначає тривалість наступного переходу. Можна використати setTimeout із функцією очищення і після кожної фази запланувати один наступний перехід.

Додатковий варіант — дозволити користувачу змінювати базову тривалість через елемент керування. У такому разі нове значення тривалості стає реактивною залежністю ефекту, а старий таймер setTimeout/інтервал має коректно очищатися під час зміни налаштування.

Це завдання не повинно погіршувати базову гарантію: у кожний момент існує лише один актуальний таймер автоматичного режиму.

3.11. Поза основним обсягом ЛР3#

У цій роботі не потрібно переносити стан між сторінками або робити його глобальним. Багатомаршрутний SPA і спільний стан світлофора з’являться в ЛР4.

Так само поза основним обсягом ЛР3 залишаються:

  • серверне збереження та GAS API;

  • Tailwind CSS і DaisyUI як система інтерфейсу;

  • автентифікація та захищений доступ;

  • інфраструктура публікації та розгортання.

Зосередьтеся на життєвому циклі одного локального автоматичного світлофора та коректній синхронізації стану React з API таймерів.

3.12. Результат#

CP3: працездатний React-застосунок «Світлофор», який зберігає ручну взаємодію і статистику CP2, має керований автоматичний/ручний режим, автоматично проходить цикл red → yellow → green → yellow → red, створює й очищає таймер у useEffect, не накопичує дубльованих таймерів після повторних запусків і зупинок та показує візуальний перехід, керований станом активного сигналу.

Цей стан проєкту є вхідною точкою для ЛР4, де локальний, але вже нетривіальний стан світлофора буде використано в багатомаршрутному SPA і винесено до спільного контексту.
