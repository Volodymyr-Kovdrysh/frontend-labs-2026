5. Лабораторна робота №5. Асинхронні дані та GAS API#

Контрольна точка: CP5

5.1. Мета роботи#

Навчитися відрізняти стан застосунку в пам’яті (runtime state) від даних, збережених на сервері, побудувати мінімальний контракт взаємодії клієнтської частини (frontend) із серверною частиною (backend) через Google Apps Script (GAS) Web App, ізолювати логіку обміну даними від компонентів представлення та явно показувати стан завантаження, успішного виконання і помилки під час асинхронних операцій.

У цій роботі ми не перетворюємо «Світлофор» на повноцінну серверну систему. Потрібна лише обмежена серверна можливість: прочитати збережений стан світлофора та явно зберегти поточний сигнал.

5.2. Результати навчання#

Після виконання роботи ви повинні вміти:

  • пояснити різницю між станом застосунку в пам’яті та даними, збереженими на сервері;

  • описати мінімальний контракт запиту й відповіді незалежно від конкретного інтерфейсу;

  • створити Google Sheet як просте серверне сховище для навчальної колекції;

  • реалізувати doGet(e) і doPost(e) у Google Apps Script Web App;

  • повертати стабільну JSON-обгортку {ok, data, error};

  • виконувати асинхронні GET/POST-запити через fetch;

  • винести логіку обміну даними до окремого модуля trafficLightsApi;

  • представляти loading, success і error як точні значення стану запиту та пояснювати їх українською;

  • показувати кнопку «Повторити» після невдалого початкового запиту;

  • зберігати поточний сигнал тільки після явної дії користувача;

  • підтверджувати успішне збереження відповіддю сервера або повторним GET-запитом;

  • перевірити збереження даних через перезавантаження браузера і новий GET-запит.

5.3. Передумови та початковий стан проєкту#

Початкова точка цієї роботи — CP4 після ЛР4:

  • застосунок є SPA з кількома маршрутами;

  • доступні маршрути /, /traffic-light, /stats і маршрут для невідомої адреси;

  • стан світлофора в пам’яті має спільного власника у TrafficLightsProvider;

  • TrafficLightPage і StatsPage читають узгоджений спільний стан;

  • поточна фаза / сигнал, лічильники, орієнтація та автоматичний/ручний режим зберігаються під час навігації маршрутами;

  • ефект таймера й очищення з ЛР3 уже належать межі провайдера контексту;

  • перезавантаження браузера все ще може повернути стан застосунку до початкового.

Новий React-проєкт не створюйте. Продовжуйте той самий наскрізний проєкт «Світлофор».

Важливо

Головна тема ЛР5 — зв’язок стану застосунку в пам’яті з даними, збереженими на сервері, через чітку межу API.

Автоматичний таймер із ЛР3 не повинен записувати стан у GAS на кожному тіку. Серверний запис виконується тільки після явної дії користувача «Зберегти поточний сигнал».

5.4. Теоретичний мінімум#

5.4.1. Стан застосунку в пам’яті й дані, збережені на сервері, — не одне й те саме#

До CP4 усі зміни існують у пам’яті браузера:

стан React
    ↓
відтворення інтерфейсу
    ↓
навігація маршрутами зберігає провайдер контексту

Але повне перезавантаження створює стан застосунку в пам’яті заново. Якщо після перезавантаження нам потрібно відновити значення, воно має існувати поза поточним процесом JavaScript.

У ЛР5 з’являється друга область даних:

стан у пам'яті браузера            серверне сховище
-----------------------            ----------------
TrafficLightsProvider   ← API →    Google Sheet
поточна фаза                       id
лічильники                         current_signal
орієнтація
режим

Сервер не повинен зберігати всі значення лише тому, що вони є в Context. У базовій моделі CP5 сервер зберігає тільки:

{
  "id": "main",
  "currentSignal": "red"
}

Лічильники, орієнтація та автоматичний/ручний режим залишаються даними стану в пам’яті.

5.4.2. Чому Google Sheet є сховищем, а не API#

React-клієнт не читає Google Sheet напряму. Таблиця є серверним сховищем, а GAS Web App є межею серверної взаємодії:

React SPA
   ↓ fetch
GAS Web App
   ↓ SpreadsheetApp
Google Sheet

Так інтерфейс знає лише контракт API, а серверна частина приховує спосіб доступу до таблиці.

5.4.3. Мінімальна колекція#

Створіть окрему електронну таблицю і лист:

TRAFFIC_LIGHTS

Мінімальна схема:

id

current_signal

main

red

id є стабільним ідентифікатором. current_signal може бути тільки одним із:

red | yellow | green

У базовій ЛР5 одного запису main достатньо. Контракт API допускає колекцію, але ми не додаємо інтерфейс вибору або CRUD лише заради демонстрації серверної частини.

5.4.4. Конфігурація не повинна бути базою даних#

Spreadsheet ID потрібний GAS, щоб відкрити сховище. Не записуйте його прямо в Code.gs. Збережіть ID у Script Property:

DB_SPREADSHEET_ID

Отже:

Script Property     → конфігурація
рядки Google Sheet  → збережені предметні дані

Це різні відповідальності.

5.4.5. Контракт API перед кодом#

У базовому CP5 є рівно дві можливості.

Читання:

GET <WEB_APP_EXEC_URL>?action=list

Успішна відповідь:

{
  "ok": true,
  "data": {
    "trafficLights": [
      {
        "id": "main",
        "currentSignal": "red"
      }
    ]
  },
  "error": null
}

Оновлення:

POST <WEB_APP_EXEC_URL>
Content-Type: text/plain;charset=utf-8

Тіло запиту є JSON-текстом:

{
  "action": "updateState",
  "id": "main",
  "currentSignal": "green"
}

Успішна відповідь:

{
  "ok": true,
  "data": {
    "trafficLight": {
      "id": "main",
      "currentSignal": "green"
    }
  },
  "error": null
}

5.4.6. Чому відповідь має обгортку#

Успіх і помилка мають однакову зовнішню форму:

{
  ok,
  data,
  error
}

Відповідь із помилкою, наприклад:

{
  "ok": false,
  "data": null,
  "error": {
    "code": "invalid_signal",
    "message": "Unsupported traffic-light signal"
  }
}

Клієнт не повинен вважати, що HTTP 200 автоматично означає успіх операції предметної області. Він перевіряє payload.ok.

5.4.7. Чому POST використовує text/plain#

Для базового профілю надсилайте JSON-текст із заголовком:

Content-Type: text/plain;charset=utf-8

і не додавайте власних заголовків.

Цей профіль обміну вже придатний для запиту з браузера через перенаправлення Apps Script ContentService. fetch має дозволити перенаправлення за замовчуванням.

Не замінюйте text/plain на application/json тільки тому, що тіло містить JSON: у цій лабораторній важливий не «красивий REST», а обмежений контракт обміну, перевірений для шляху браузер → GAS Web App.

5.4.8. /exec і /dev — різні URL розгортання#

Для результату лабораторної використовуйте версійне розгортання Web App і URL, що закінчується на:

/exec

/dev може бути корисним для тестування розробником, але не є основною URL-адресою розгортання для лабораторного результату.

Доступ має дозволяти браузерному клієнту звертатися до Web App без окремого потоку Google OAuth. Точний текст параметра доступу може відрізнятися залежно від типу облікового запису Google або політики організації.

Попередження

Ця серверна частина містить лише несекретні навчальні дані й не є моделлю захисту для виробничого середовища. Автентифікація та захищена межа застосунку з’являться у ЛР7, але вони не перетворюють цей GAS Web App автоматично на API з виробничою авторизацією.

5.4.9. Межа доступу до даних#

Компоненти представлення не повинні знати:

  • GAS URL;

  • параметри fetch;

  • параметр запиту action=list;

  • форму тіла POST-запиту;

  • логіку розбору JSON-обгортки;

  • деталі перенаправлення ContentService.

Це відповідальність окремого модуля:

src/
└── api/
    └── trafficLightsApi.js

Його відкритий інтерфейс:

listTrafficLights()
updateTrafficLightState(id, currentSignal)

Сторінка/провайдер контексту працює зі значеннями предметної області, а не з деталями обміну даними.

5.4.10. Стан запиту — це окремий стан застосунку#

Асинхронна операція не має лише двох станів «дані є / даних немає».

Мінімально потрібні:

idle | loading | success | error

Наприклад:

початковий GET-запит
   ↓
loading
   ├── success → дані доступні
   └── error   → видиме повідомлення + «Повторити»

Для збереження аналогічно:

натискання «Зберегти поточний сигнал»
   ↓
loading
   ├── success → сервер підтвердив збережений запис
   └── error   → не вдавати, що збереження відбулося

5.4.11. Поточний сигнал у пам’яті й збережений на сервері сигнал можуть тимчасово відрізнятися#

Це важлива частина роботи.

Наприклад:

збережений сигнал на сервері = red
сигнал у пам'яті             = green

Такий стан є нормальним до натискання «Зберегти поточний сигнал».

Після успішного збереження:

збережений сигнал на сервері = green
сигнал у пам'яті             = green

Отже кнопка «Зберегти поточний сигнал» має зміст саме тому, що стан у пам’яті й дані на сервері не синхронізуються автоматично на кожну зміну.

5.4.12. Особливість yellow у моделі фаз#

У ЛР3 автоматичний цикл мав дві фази yellow:

red → yellow → green → yellow → red

А серверна модель CP5 зберігає лише видимий сигнал:

red | yellow | green

Тому збережений на сервері yellow не зберігає напрям циклу. Якщо єдиним джерелом актуального стану в пам’яті є індекс фази, під час початкового завантаження виберіть одну узгоджену фазу yellow, наприклад першу.

Схематично:

серверний red    → фаза red у пам'яті
серверний yellow → узгоджена фаза yellow у пам'яті
серверний green  → фаза green у пам'яті

Не розширюйте серверну модель полем phase лише для усунення цієї неоднозначності: у CP5 ми зберігаємо видимий поточний сигнал, а не всю модель станів таймера.

5.5. Постановка задачі#

Розширте CP4 так, щоб запис main із поточним сигналом можна було прочитати з Google Sheet через GAS Web App і явно зберегти назад на сервер.

Після виконання роботи застосунок повинен:

  1. під час початкового завантаження виконати GET-запит колекції з GAS;

  2. показати стан завантаження, доки запит не завершився;

  3. після успішного виконання знайти запис main і відобразити збережений сигнал;

  4. синхронізувати сигнал у пам’яті із завантаженим сигналом із сервера;

  5. у разі помилки показати повідомлення та кнопку «Повторити»;

  6. зберегти поведінку CP1–CP4 у пам’яті такою, як раніше;

  7. не виконувати серверний запис на кожному кроці автоматичного таймера;

  8. мати явний елемент керування «Зберегти поточний сигнал»;

  9. під час збереження показувати стан очікування/виконання запиту і блокувати повторне збереження;

  10. після успішного виконання прийняти оновлений запис, повернутий сервером;

  11. після помилки показати, що серверне збереження не підтверджено;

  12. після перезавантаження браузера прочитати з GAS те саме раніше збережене значення.

5.6. Виконання#

5.6.1. Крок 1. Створіть серверне сховище#

Створіть Google Spreadsheet для навчальної серверної частини.

Перейменуйте перший аркуш на:

TRAFFIC_LIGHTS

Додайте:

A

B

id

current_signal

main

red

Не додавайте десятки тестових стовпців. У базовому контракті використовуються тільки id та current_signal.

Скопіюйте Spreadsheet ID із URL. У URL виду:

https://docs.google.com/spreadsheets/d/<SPREADSHEET_ID>/edit

потрібна саме частина <SPREADSHEET_ID>.

Перевірка 1: аркуш називається TRAFFIC_LIGHTS, а рядок main | red однозначно читається як один серверний запис.

5.6.2. Крок 2. Створіть вихідний код GAS у репозиторії#

У наскрізному студентському репозиторії створіть:

gas/
└── Code.gs

Цей файл є копією вихідного коду серверної частини в репозиторії. Той самий код вставте у проєкт Apps Script, прив’язаний до вашого навчального розгортання.

Не кладіть вихідний код серверної частини випадково в React src/components і не називайте його компонентом представлення.

Перевірка 2: у репозиторії є явний gas/Code.gs, а вихідний код React і GAS мають різні межі відповідальності.

5.6.3. Крок 3. Додайте Script Property#

У проєкті Apps Script відкрийте налаштування проєкту і створіть Script Property:

DB_SPREADSHEET_ID=<ваш Spreadsheet ID>

У Code.gs отримуйте конфігурацію через PropertiesService:

const spreadsheetId = PropertiesService
  .getScriptProperties()
  .getProperty("DB_SPREADSHEET_ID")

Потім відкривайте сховище:

const sheet = SpreadsheetApp
  .openById(spreadsheetId)
  .getSheetByName("TRAFFIC_LIGHTS")

Якщо властивість або аркуш відсутні, серверна частина має завершити операцію контрольованою помилкою, а не мовчки працювати з випадковою таблицею.

Перевірка 3: DB_SPREADSHEET_ID не записується жорстко у Code.gs, а GAS може відкрити потрібний аркуш TRAFFIC_LIGHTS.

5.6.4. Крок 4. Реалізуйте допоміжні функції JSON-відповідей#

Створіть одну допоміжну функцію, яка повертає JSON через ContentService:

function json_(payload) {
  return ContentService
    .createTextOutput(JSON.stringify(payload))
    .setMimeType(ContentService.MimeType.JSON)
}

Для успішної відповіді зручно мати:

function jsonOk_(data) {
  return json_({
    ok: true,
    data,
    error: null,
  })
}

Для відповіді з помилкою:

function jsonError_(code, message) {
  return json_({
    ok: false,
    data: null,
    error: { code, message },
  })
}

Точний набір внутрішніх назв допоміжних функцій може відрізнятися. Важливий відкритий контракт: {ok,data,error}.

Перевірка 4: успішна відповідь і відповідь із помилкою мають однакову форму обгортки.

5.6.5. Крок 5. Реалізуйте GET-запит колекції#

doGet(e) повинен підтримувати команду:

action=list

Алгоритм:

  1. перевірити e.parameter.action;

  2. відкрити TRAFFIC_LIGHTS;

  3. прочитати рядки;

  4. пропустити заголовок;

  5. перетворити кожний рядок на об’єкт {id,currentSignal};

  6. повернути колекцію через jsonOk_;

  7. у випадку помилки повернути jsonError_.

Базова форма:

function doGet(e) {
  try {
    const action = e?.parameter?.action

    if (action !== "list") {
      return jsonError_("unknown_action", "Unsupported action")
    }

    return jsonOk_({
      trafficLights: listTrafficLights_(),
    })
  } catch (error) {
    return jsonError_("storage_error", error.message)
  }
}

Не додавайте кінцеві точки створення/видалення.

Перевірка 5: GET-запит колекції повертає main із полем currentSignal у camelCase для клієнта, навіть якщо стовпець у Sheet називається current_signal.

5.6.6. Крок 6. Реалізуйте оновлення одного запису#

doPost(e) отримує JSON-текст у e.postData.contents.

Потрібно перевірити:

  • тіло запиту можна розібрати;

  • action === "updateState";

  • id переданий;

  • currentSignal належить red | yellow | green;

  • запис із таким id існує.

Після перевірки знайдіть потрібний рядок, оновіть лише current_signal і поверніть оновлений запис після збереження.

Каркас:

function doPost(e) {
  try {
    const command = JSON.parse(e?.postData?.contents || "{}")

    if (command.action !== "updateState") {
      return jsonError_("unknown_action", "Unsupported action")
    }

    // перевірити id і currentSignal
    // оновити відповідний рядок

    return jsonOk_({
      trafficLight: updatedRecord,
    })
  } catch (error) {
    return jsonError_("bad_request", error.message)
  }
}

Не повертайте успіх до фактичного оновлення сховища.

Перевірка 6: коректне оновлення змінює тільки потрібний рядок, а некоректний сигнал не записується як довільний текст.

5.6.7. Крок 7. Створіть версійне розгортання Web App#

У Apps Script створіть розгортання типу Web app.

Для базової лабораторної:

  • виконання — від імені власника/розробника;

  • доступ — браузерний клієнт має звертатися без окремого потоку OAuth;

  • використовуйте версійну URL-адресу /exec.

Збережіть URL-адресу /exec. Це адреса розгортання, а не пароль чи секрет API.

Якщо політика вашого облікового запису Google не дозволяє потрібний режим доступу, зафіксуйте це як обмеження середовища і зверніться до викладача. Не додавайте самостійно OAuth/proxy лише для обходу політики.

Перевірка 7: у браузері доступне версійне розгортання /exec, а не лише URL /dev, доступний з редактора.

5.6.8. Крок 8. Перевірте контракт GAS окремо від React-інтерфейсу#

До інтеграції з провайдером контексту переконайтеся, що контракт серверної частини працює самостійно.

GET:

<WEB_APP_EXEC_URL>?action=list

має повернути обгортку з колекцією.

Для POST використайте браузерну/клієнтську перевірку або тимчасовий пробний запит, який надсилає:

fetch(WEB_APP_EXEC_URL, {
  method: "POST",
  headers: {
    "Content-Type": "text/plain;charset=utf-8",
  },
  body: JSON.stringify({
    action: "updateState",
    id: "main",
    currentSignal: "green",
  }),
})

Після POST перевірте також сам Google Sheet.

Перевірка 8: читання/запис серверної частини працює незалежно від того, чи правильно відображений React-інтерфейс.

5.6.9. Крок 9. Створіть trafficLightsApi.js#

У вихідному коді React створіть:

src/
└── api/
    └── trafficLightsApi.js

У базовій ЛР5 тільки цей модуль знає URL Web App і деталі виклику fetch.

На початку можна зберегти URL розгортання у константі модуля:

const API_URL = "<ваш versioned /exec URL>"

Цей URL не є секретом. Не записуйте сюди Spreadsheet ID і не намагайтеся з браузера напряму відкривати Sheet.

Створіть допоміжну функцію для розбору обгортки:

async function parseEnvelope(response) {
  const payload = await response.json()

  if (!payload.ok) {
    throw new Error(payload.error?.message || "GAS request failed")
  }

  return payload.data
}

Відкрита функція читання:

export async function listTrafficLights() {
  const response = await fetch(`${API_URL}?action=list`)
  const data = await parseEnvelope(response)

  return data.trafficLights
}

Відкрита функція оновлення:

export async function updateTrafficLightState(id, currentSignal) {
  const response = await fetch(API_URL, {
    method: "POST",
    headers: {
      "Content-Type": "text/plain;charset=utf-8",
    },
    body: JSON.stringify({
      action: "updateState",
      id,
      currentSignal,
    }),
  })

  const data = await parseEnvelope(response)
  return data.trafficLight
}

Не викликайте fetch напряму повторно в TrafficLightPage, StatsPage, Light або StatsBar.

Перевірка 9: пошук fetch( у вихідному коді застосунку показує виклик обміну даними у trafficLightsApi.js, а не розсипані виклики по компонентах представлення.

5.6.10. Крок 10. Додайте стан серверного запиту до межі провайдера контексту#

TrafficLightsProvider уже є спільним власником стану застосунку в CP4. Розширте його лише настільки, наскільки потрібно CP5.

Наприклад, потрібні значення:

serverTrafficLights
loadStatus
loadError
saveStatus
saveError

Можна використовувати інші назви або об’єднати статуси, якщо поведінка лишається однозначною. Не створюйте універсальне глобальне сховище.

Додайте дії предметної області/застосунку:

reloadTrafficLights()
saveCurrentSignal()

Сторінка представлення має викликати дію, а не формувати POST-запит сама.

Перевірка 10: провайдер контексту керує асинхронним станом застосунку, а деталі обміну даними залишаються всередині trafficLightsApi.js.

5.6.11. Крок 11. Реалізуйте початкове завантаження через ефект#

Під час монтування провайдера контексту виконайте початковий GET-запит.

Схематично:

useEffect(() => {
  reloadTrafficLights()
}, [])

Сам reloadTrafficLights повинен:

  1. перейти в loading;

  2. очистити попередню помилку завантаження;

  3. викликати listTrafficLights();

  4. знайти запис main;

  5. зберегти серверну колекцію;

  6. синхронізувати сигнал у пам’яті зі збереженим currentSignal;

  7. перейти в success;

  8. у разі винятку перейти в error.

Пам’ятайте про неоднозначність фази yellow: якщо єдине джерело актуального стану CP3 — індекс фази, створіть невелике детерміноване відображення із серверного сигналу в узгоджену фазу.

Примітка

Початкове завантаження із сервера не повинно запускати окремий серверний запис. Спочатку ми читаємо збережений серверний стан і відновлюємо його представлення в пам’яті.

У режимі розробки React StrictMode може виконати додатковий цикл налаштування/очищення і ви можете побачити повторний початковий GET. Це корисна перевірка того, що операція читання не має небезпечних побічних ефектів. Не вимикайте StrictMode лише щоб приховати повторний GET. Натомість POST-збереження повинно залишатися прив’язаним до явної дії користувача і не запускатися з цього ефекту.

Перевірка 11: після перезавантаження застосунок показує поточний сигнал, прочитаний із GAS, а не завжди жорстко заданий початковий red; у режимі розробки повторний GET не спричиняє дубльованих серверних записів.

5.6.12. Крок 12. Покажіть стани завантаження, помилки та кнопку «Повторити»#

На сторінці або інтеграційному компоненті покажіть явні стани.

Під час початкового завантаження:

Завантаження даних світлофора…

У разі помилки:

Не вдалося завантажити збережений серверний стан.
[Повторити]

Кнопка «Повторити» повинна викликати reloadTrafficLights().

Не приховуйте помилку лише в консолі браузера.

Для перевірки стану помилки тимчасово:

  • зіпсуйте API URL;

  • або використайте інший контрольований спосіб спричинити помилку запиту;

  • переконайтеся, що інтерфейс показує помилку;

  • поверніть правильний URL;

  • натисніть «Повторити».

Перевірка 12: студент може продемонструвати не лише успішний сценарій, а й послідовність помилка → «Повторити» → успішне виконання.

5.6.13. Крок 13. Додайте явне «Зберегти поточний сигнал»#

На /traffic-light додайте кнопку або еквівалентний елемент керування:

Зберегти поточний сигнал

Дія повинна взяти поточний сигнал у пам’яті і викликати:

updateTrafficLightState("main", currentSignal)

Поки POST виконується:

  • показуйте стан очікування/виконання запиту;

  • зробіть кнопку збереження недоступною, щоб повторні натискання не створювали зайвих запитів.

Після успішного виконання:

  • прийміть оновлений запис із відповіді сервера;

  • оновіть копію даних, підтверджену сервером;

  • покажіть коротке підтвердження успіху або підтверджене сервером збережене значення.

Після помилки:

  • покажіть помилку;

  • не змінюйте інтерфейс так, ніби серверне збереження гарантовано відбулося.

Перевірка 13: кнопка збереження має зрозумілу поведінку під час очікування, успішного виконання та помилки і не є просто локальним setState.

5.6.14. Крок 14. Не синхронізуйте таймер із сервером автоматично#

Увімкніть автоматичний режим і поспостерігайте за кількома кроками таймера.

Під час кроків таймера:

  • сигнал у пам’яті змінюється;

  • збережений на сервері сигнал не зобов’язаний змінюватися;

  • вкладка мережевих запитів не повинна показувати POST на кожний крок таймера.

Тільки явне збереження створює оновлення даних на сервері.

Це означає, що можна мати:

сигнал у пам'яті = yellow
сигнал на сервері = green

і це очікувано до наступного збереження.

Перевірка 14: автоматичний цикл не створює циклу серверних записів.

5.6.15. Крок 15. Перевірте наскрізне збереження даних на сервері#

Виконайте сценарій:

  1. відкрийте /traffic-light;

  2. дочекайтеся успішного початкового GET-запиту;

  3. встановіть сигнал у пам’яті, відмінний від серверного значення;

  4. переконайтеся, що до збереження змінено лише стан у пам’яті;

  5. натисніть «Зберегти поточний сигнал»;

  6. дочекайтеся підтвердження сервера;

  7. перевірте відповідний рядок у Google Sheet;

  8. перезавантажте браузер;

  9. дочекайтеся нового GET-запиту;

  10. переконайтеся, що застосунок відновив раніше збережений сигнал.

Саме кроки 7–10 доводять збереження даних на сервері. Навігація маршрутами без перезавантаження цього не доводить — воно вже було частиною CP4.

Перевірка 15: збережене значення переживає повне перезавантаження браузера і повертається через новий GET-запит.

5.7. Контрольні точки виконання#

Перед завершенням роботи продемонструйте п’ять ключових перевірок:

  1. GET і POST через версійний /exec використовують обгортку {ok,data,error}, а некоректний сигнал не записується у Sheet;

  2. початковий GET-запит показує завантаження, помилку й кнопку «Повторити», а після успіху відновлює запис main у стані застосунку;

  3. «Зберегти поточний сигнал» виконує явний POST з text/plain;charset=utf-8, тимчасово блокує повторне збереження і приймає оновлений запис із сервера;

  4. автоматичний таймер не створює POST-запитів, а зміна в Google Sheet переживає перезавантаження й повертається новим GET-запитом;

  5. маршрутизація CP4, спільний стан, trafficLightsApi.js як єдине місце прямого обміну даними та очищення таймера продовжують працювати.

5.9. Критерії приймання#

Робота вважається виконаною, якщо одночасно виконані всі умови:

  • застосунок продовжує CP4 без створення нового незалежного React-проєкту;

  • є Google Sheet TRAFFIC_LIGHTS зі стабільним записом main;

  • вихідний код GAS збережений у репозиторії як gas/Code.gs;

  • Spreadsheet ID не записується жорстко у вихідному коді GAS, а читається через DB_SPREADSHEET_ID Script Property;

  • Web App підтримує GET-запит колекції й оновлення поточного сигналу одного запису;

  • відкритий контракт відповіді використовує {ok,data,error};

  • некоректний/невідомий запит не записує довільні значення в Sheet;

  • використовується версійне розгортання /exec;

  • межа обміну даними React реалізована у src/api/trafficLightsApi.js;

  • сторінки/компоненти представлення не містять дубльованих прямих викликів fetch;

  • початковий GET-запит має видимий стан завантаження;

  • невдалий GET-запит має видимий стан помилки та кнопку «Повторити»;

  • успішний GET-запит дає підтверджений сервером запис main;

  • поточний сигнал у пам’яті відновлюється зі збереженого серверного значення;

  • явне збереження виконує POST з text/plain;charset=utf-8 без власних заголовків;

  • під час збереження інтерфейс показує, що запит виконується;

  • успішне збереження підтверджується записом із відповіді сервера або повторним GET-запитом;

  • невдале збереження не видається за підтверджене збереження даних;

  • автоматичний таймер не виконує серверний запис на кожному кроці;

  • фактичне значення Google Sheet змінюється після підтвердженого збереження;

  • перезавантаження браузера + новий GET-запит повертають раніше збережений сигнал;

  • студент може пояснити межу React UI → trafficLightsApi → GAS → Sheet;

  • маршрути CP4, власник стану в Context і очищення таймера CP3 збережені.

Після виконання базових вимог можна додати одне обмежене розширення:

створіть ще один запис у TRAFFIC_LIGHTS, наприклад:

secondary | yellow

і покажіть колекцію в окремій частині інтерфейсу лише для читання.

Не додавайте API створення/видалення. Новий рядок можна створити вручну в таблиці. Мета розширення — показати, що контракт GET уже повертає колекцію, а не перетворити ЛР5 на CRUD.

Як альтернатива, можна коротко використати json-server як локальну імітацію сервера для налагодження клієнтської межі, але фінальний CP5 усе одно повинен працювати із серверним сховищем GAS.

5.11. Поза основним обсягом ЛР5#

У цій роботі не потрібно реалізовувати:

  • створення/видалення записів через API;

  • пагінацію, пошук або фільтрацію;

  • оптимістичний контроль конкурентних змін / версіонування;

  • автономний режим;

  • синхронізацію в реальному часі;

  • POST на кожний крок автоматичного таймера;

  • Redux/RTK Query/TanStack Query або іншу бібліотеку кешу/стану лише заради цього потоку запитів;

  • автентифікацію користувача;

  • серверну модель авторизації;

  • OAuth/JWT;

  • керування секретами у виробничому середовищі;

  • clasp, CI/CD або автоматизоване розгортання Apps Script;

  • виробничий рівень журналювання/спостережуваності;

  • складний REST-маршрутизатор або окрему серверну частину Node.

Ці теми можуть бути корисними в реальних системах, але вони змінюють основну тему цієї лабораторної.

5.12. Результат#

CP5: React SPA з кількома маршрутами та спільним станом світлофора в пам’яті й обмеженою серверною частиною GAS. Google Sheet TRAFFIC_LIGHTS зберігає {id,currentSignal}, GAS Web App дає читання колекції та явне оновлення, а React ізолює логіку обміну у trafficLightsApi.js. Початкове завантаження має стани loading/error/success, збереження виконується лише за явною дією користувача, автоматичний таймер не створює циклу серверних записів, а перезавантаження браузера + новий GET-запит підтверджують збереження даних.

Цей стан проєкту є вхідною точкою для ЛР6, де функціональну поведінку CP5 буде оформлено як послідовний інтерфейс із Tailwind CSS та DaisyUI.
